# Программа подготовки к работе над Spine

В каталоге находятся два направления подготовки:

1. [База знаний и агент вопросов и ответов](01-knowledge-base-and-qa.md).
2. [Ассистент для подготовки коммерческих предложений](02-commercial-proposal-assistant.md).

Готовые исходные документы и проверочные примеры находятся в каталоге
[`synthetic-data/`](synthetic-data/README.md). Необходимо использовать эти файлы,
а не создавать исходные данные самостоятельно.

Готовые вымышленные исходные данные находятся в каталоге
`[synthetic-data/](synthetic-data/README.md)`. В нём есть документы, исторические кейсы, сметы, ошибочные примеры, настройки заглушек и размеченные наборы для автоматических проверок. Разработчику не нужно придумывать исходные данные перед началом реализации.

Каждое направление состоит из десяти небольших инфраструктурных заданий. Они создаются с нуля и не требуют доступа к какому-либо существующему репозиторию.

## Для чего нужна программа

После выполнения заданий разработчик будет готов реализовывать и проверять небольшие инфраструктурные части Spine. Разработчик последовательно освоит:

- типизированные контракты на Pydantic;
- собственные интерфейсы и заменяемые адаптеры к внешним библиотекам;
- неизменяемые редакции и происхождение данных;
- безопасную повторную обработку без создания дубликатов;
- локальное хранение в JSONL и SQLite;
- асинхронные операции;
- Cognee как графовую и векторную проекцию;
- FastAPI и проверки программных интерфейсов;
- процессы и операции Temporal, сигналы, запросы состояния, повторные попытки и
проверки с ускоренным временем;
- автономные проверки качества и пороги готовности;
- процессы с обязательным участием человека;
- детерминированную арифметику.

## Требования к рабочему месту

- Python 3.11 или новее;
- `uv`;
- Git;
- редактор кода;
- возможность запустить локальный HTTP-сервер.

Docker, PostgreSQL, Redis, Kubernetes и облачный Temporal не требуются.

Для заданий с языковой моделью используется один из вариантов:

1. ключ API в переменной окружения;
2. локальная модель;
3. готовая программная заглушка — обязательный вариант для автоматических проверок.

## Как создавать решения заданий

Каждое задание выполняется в отдельном каталоге:

```text
intern-tasks/
  01-source-revisions/
  02-document-chunks/
  03-ingestion-runner/
  ...
```

Минимальная структура одной работы:

```text
task-name/
  pyproject.toml
  README.md
  src/task_name/
  tests/
  data/fixtures/
  .env.example
```

Рекомендуемый `pyproject.toml` для начала:

```toml
[project]
name = "task-name"
version = "0.1.0"
requires-python = ">=3.11"
dependencies = ["pydantic>=2.8"]

[project.optional-dependencies]
dev = ["pytest>=8", "pytest-asyncio>=0.23", "httpx>=0.27"]

[tool.pytest.ini_options]
asyncio_mode = "auto"
pythonpath = ["src"]
```

Зависимости Cognee, FastAPI и Temporal добавляются только в тех заданиях, где они
действительно используются.

## Единые правила реализации

1. Код предметных правил не импортирует FastAPI, Cognee, Temporal или SQLite.
2. Внешняя библиотека располагается за собственным интерфейсом `Protocol`.
3. В проверках по умолчанию не выполняются сетевые запросы.
4. Все идентификаторы рабочей области передаются явно.
5. Вывод, влияющий на ответ или документ, хранит ссылки на исходные данные.
6. Повтор команды с тем же ключом повторяемости не создаёт второй результат.
7. Ошибка одного элемента не должна скрывать результат обработки остальных.
8. Секреты читаются из переменных окружения и не записываются в Git или журналы.
9. Реальные документы клиентов запрещены; используются только синтетические примеры.
10. README содержит команды, которые наставник может скопировать и выполнить.

## Общие критерии приёмки

Задание принято, если одновременно выполнены все условия:

- обязательные сценарии воспроизводятся по README;
- автоматические проверки проходят;
- внешняя библиотека скрыта за собственным интерфейсом;
- обработаны ошибки и повторный запуск;
- сохранены ссылки на источники и изоляция рабочих областей;
- решение запускается на чистой машине.

Красивый интерфейс не компенсирует неверные данные, отсутствие проверок или
смешение рабочих областей.

## Начальная настройка каждой работы

Не создавайте файлы вручную до инициализации проекта. Для задания с именем
`source-revisions` выполните:

```bash
mkdir 01-source-revisions
cd 01-source-revisions
uv init --package --name source-revisions --python 3.11
uv add 'pydantic>=2.8,<3' 'typer>=0.12,<1'
uv add --dev 'pytest>=8,<9' 'pytest-asyncio>=0.23,<2' 'ruff>=0.6,<1'
mkdir -p data/fixtures tests
uv run pytest -q
```

Для другого решения замените имя пакета. После `uv add` обязательно сохраняйте
`uv.lock` в Git.

Во всех заданиях настройте Ruff и pytest:

```toml
[tool.pytest.ini_options]
asyncio_mode = "auto"
pythonpath = ["src"]
markers = [
  "integration: проверка с настоящей внешней библиотекой",
  "llm: проверка с настроенной языковой моделью",
]

[tool.ruff]
line-length = 100

[tool.ruff.lint]
select = ["E", "F", "I", "B", "UP"]
```

Единая локальная проверка:

```bash
uv run ruff check .
uv run pytest -q -m 'not integration and not llm'
uv run python -m compileall -q src tests
```

Проверки с настоящей внешней библиотекой запускаются отдельно и не должны неожиданно требовать
ключ или установленный сервер:

```bash
uv run pytest -q -m integration
uv run pytest -q -m llm
```

Если условие не выполнено, тест делает `pytest.skip("...reason...")`, а не падает
с неясной ошибкой подключения.

## Какие библиотеки для чего используются


| Библиотека            | Где применяется                           | Что нужно освоить                                                |
| --------------------- | ----------------------------------------- | ---------------------------------------------------------------- |
| `pydantic`            | все задания                               | Проверка внешних и межмодульных контрактов                       |
| `typer`               | задания с командной строкой               | Тонкая оболочка над прикладной службой                           |
| `pytest`              | все задания                               | Модульные, контрактные и связные проверки                        |
| `pytest-asyncio`      | асинхронные переходники                   | Проверка асинхронного кода без ручного управления циклом событий |
| `aiosqlite`           | защита от повторов и хранение результатов | Асинхронная работа с SQLite и транзакции                         |
| `structlog`           | загрузка, HTTP и длительные процессы      | Структурированные события вместо строковых журналов              |
| `cognee`              | поиск документов и аналогов               | `remember` строит память, `recall` извлекает контекст            |
| `fastapi` + `uvicorn` | HTTP-интерфейс                            | Проверка тела запроса, сборка зависимостей и обработка ошибок    |
| `httpx`               | проверки HTTP-интерфейса                  | Вызов приложения в памяти без сетевого порта                     |
| `temporalio`          | долгоживущие процессы                     | Разделение детерминированного процесса и операций ввода-вывода   |


Стандартные библиотеки `hashlib`, `pathlib`, `json`, `decimal`, `uuid` и
`datetime` следует предпочитать сторонним пакетам, когда их достаточно.
